# Как работает Facade в этом проекте

## Идея на простом примере

Игрок нажимает «Найти матч». За этой одной кнопкой должны произойти три разные вещи: создать группу подходящего рейтинга, выделить сервер с приемлемой задержкой и подтвердить матч после проверки античита. Игроку не нужно самому вызывать три сервиса и помнить, что отменять при ошибке. Эту работу берёт на себя `MatchmakingFacade`.

```text
Main → MatchmakingFacade → PartyService (A)
                         → ServerService (B)
                         → MatchService (C)

Main → AdminFacade → просмотр или ручная компенсация
```

Фасад — это простой вход к нескольким подсистемам и их общей последовательности. Подсистемы при этом остаются самостоятельными: тест может вызвать `PartyService.reserve`, `ServerService.allocate` или `MatchService.confirm` напрямую.

## Структура проекта

| Путь | Роль |
|---|---|
| `src/main/java/matchmaking/party/` | A: формирование группы, проверка рейтинга, файл группы |
| `src/main/java/matchmaking/server/` | B: проверка задержки, выделение сервера, файл выделения |
| `src/main/java/matchmaking/match/` | C: античит, подтверждение матча, файл результата |
| `MatchmakingFacade.java` | Общая цепочка и компенсация |
| `AdminFacade.java` | Просмотр состояния и ручная компенсация |
| `Workflow.java`, `WorkflowRepository.java` | Состояние всей цепочки на диске |
| `Store.java` | Чтение и атомарная запись `.properties` файлов |
| `Main.java` | Меню для живой демонстрации |
| `src/test/java/matchmaking/MatchmakingTest.java` | Тесты цепочки, рестарта и подсистем |

В каждой подсистеме ровно четыре класса. Например, у A `PartyTicket` хранит данные и разрешённые переходы `NEW → RESERVED → CANCELLED`; `RatingRule` проверяет допустимый рейтинг и размер группы; `PartyRepository` читает и пишет её файл; `PartyService` выполняет самостоятельные операции `reserve`, `cancel`, `inspect`. Аналогично у B: `ServerAllocation`, `LatencyRule`, `ServerRepository`, `ServerService`. У C: `MatchRecord`, `AntiCheatRule`, `MatchRepository`, `MatchService`.

Важно различать роли: репозиторий **сохраняет** состояние, правило **принимает решение**, сервис **выполняет операцию одной подсистемы**, фасад **координирует несколько подсистем**. Сервис A ничего не знает о B или C.

## Что происходит при успешном запуске

1. `Main` получает имя игрока, рейтинг, размер группы, ping и флаг подозрительности.
2. `MatchmakingFacade.begin` создаёт ID, записывает `Workflow` со статусом `PENDING_B`, затем вызывает `PartyService.reserve`. A сохраняет `PartyTicket` со статусом `RESERVED`.
3. `MatchmakingFacade.advance` читает `Workflow` и фактический файл A. `ServerService.allocate` проверяет ping и сохраняет `ServerAllocation` со статусом `ALLOCATED`. Фасад пишет `PENDING_C`.
4. Следующий `advance` вызывает `MatchService.confirm`. Античит пропускает игрока; C сохраняет `MatchRecord` со статусом `CONFIRMED`. Фасад пишет `COMPLETED`.

`run` просто вызывает `begin`, затем два раза `advance`. Меню запускает те же шаги отдельно, чтобы можно было увидеть состояние между ними.

## Если B или C отказал

При ping 121 мс `LatencyRule` отклоняет сервер. A уже записала `RESERVED`, но B ещё не записала выделение. Фасад сохраняет `COMPENSATING`, смотрит реальные файлы, вызывает `PartyService.cancel` и записывает `COMPENSATED`. Итог: `party=CANCELLED`, `server=NONE`, `match=NONE`.

При `suspicious=true` B уже сохранила `ALLOCATED`, а `AntiCheatRule` отклоняет C. Фасад выполняет **два** обратных шага в обратном порядке: `ServerService.release`, затем `PartyService.cancel`. Итог: `party=CANCELLED`, `server=RELEASED`, `match=NONE`. Отмена — это не удаление файлов: статусы показывают историю действий.

Если администратор отменяет уже завершённый матч, сначала `MatchService.revoke` переводит C в `REVOKED`, затем освобождается B и отменяется A. Повторная компенсация безопасна: фасад проверяет сохранённые статусы и не отменяет их второй раз.

## Как работает перезапуск

Файлы находятся в `data/party`, `data/server`, `data/match` и `data/workflow`. `Store.write` сначала пишет временный файл, затем атомарно заменяет нужный файл. После закрытия программы новые объекты считывают значения из этих файлов. Поле `PENDING_B` или `PENDING_C` говорит, где остановилась цепочка, а состояния сущностей уточняют, был ли конкретный шаг уже сохранён до внезапного закрытия.

Для проверки в меню выберите **2**, запишите ID и закройте программу. Запустите снова: **4** показывает сохранённое состояние, **3** выполняет B, ещё раз **3** выполняет C. `MatchmakingTest.restartMidChainUsesSavedProgress` автоматизирует ту же проверку. Тесты со «старым» маркером прогресса показывают, что уже сохранённые B и C не создаются повторно.

## Facade, Adapter и Principle of Least Knowledge

`Facade` скрывает от клиента последовательность A → B → C и логику отмены. `Adapter` решал бы другую проблему: преобразовал бы несовместимый интерфейс одного сервиса в ожидаемый формат. Здесь интерфейсы подсистем не требуется преобразовывать.

**Principle of Least Knowledge:** клиенту достаточно знать `MatchmakingFacade.run(...)`; ему не нужны `PartyRepository`, `ServerRepository`, `MatchRepository` и правила. Без фасада клиенту пришлось бы обращаться ко всем трём сервисам и самому выбирать глубину компенсации. Конкретные фрагменты «до/после» есть в README.

## Что объяснить на защите

1. **Почему два фасада?** `MatchmakingFacade` делает обычный путь игрока, `AdminFacade` даёт узкие операции проверки и ручной отмены.
2. **Почему это настоящая персистентность?** Каждый gateway записывает файл; после перезапуска новые объекты восстанавливают и сущности, и прогресс. В тестах создаётся новый `Store` на том же пути.
3. **Почему два уровня компенсации?** B может отказать после сохранения A; C может отказать после сохранения A и B. Во втором случае отменяются B, потом A.
4. **Кто защищает статусы?** Методы `PartyTicket.reserve/cancel`, `ServerAllocation.allocate/release`, `MatchRecord.confirm/revoke`. Переход из неверного статуса бросает исключение независимо от фасада.
5. **Как тесты соблюдают F.I.R.S.T.?** `@TempDir` изолирует файл каждого теста, проверки быстрые и повторяемые, результат определяется `assert`-проверками, тесты зафиксированы вместе с кодом. Помощник `gameAt(disk)` делает сценарии читаемыми.

Короткое определение для ответа: **Facade даёт клиенту один понятный вызов для сложной работы нескольких независимых подсистем, не лишая подсистем самостоятельности.**
